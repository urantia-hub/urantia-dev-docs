## Install

```bash
npm install @urantia/auth
```

## Overview

`@urantia/auth` signs people in through [accounts.urantiahub.com](https://accounts.urantiahub.com). A person signs in once with a 6-digit email code or with Google, sees what your app asks for, and allows it. Your app then gets tokens for the parts of the API that the person allowed.

The package has two entries:

| Entry | Use it for |
|-------|-----------|
| `@urantia/auth/server` | An app with a backend. The tokens stay on your server. This is the recommended way. |
| `@urantia/auth` | An app that runs only in the browser. |

<Info>
  The content API itself needs no key and no account. You only need this package for a person's own data: bookmarks, notes, reading progress, and reader settings.
</Info>

## Register your app

<Steps>
  <Step title="Open the developer pages">
    Go to [accounts.urantiahub.com/apps](https://accounts.urantiahub.com/apps) and sign in with your UrantiaHub account.
  </Step>
  <Step title="Register an app">
    Press **Register an app** and fill in:
    - **Name**: people see it on the sign-in page.
    - **App ID**: small letters, numbers, and hyphens. It can never change, because your code uses it.
    - **What does the app do?**: two or three sentences for the reviewer.
    - **Return address**: where people land after they sign in (also called a redirect URI). Use `http://localhost:3000/callback` for local work.
    - **What the app can do**: the permissions that your app needs. Ask only for what you use.
  </Step>
  <Step title="Save the secret">
    You see the **App ID** and the **App secret**. The secret is shown one time.

    <Warning>
      Keep the secret where only your server can read it. Never put it in browser code, in a mobile app, or in a repository. If it leaks or you lose it, make a new one on the app page. The old one stops at once.
    </Warning>
  </Step>
  <Step title="Build while it is in review">
    A new app works for you at once, so you can build and test. Other people can sign in after a reviewer approves it, which takes a few days at most. You get an email with the decision.
  </Step>
</Steps>

A later change to the name, the logo, a return address, or a permission goes to a reviewer first. Your app keeps working as it is until the change is approved. A change of a color, and a removal of an address or a permission, are live at once.

## Server flow (recommended)

```typescript
import {
  createAuthorizeUrl,
  exchangeCode,
  refreshTokens,
  revokeTokens,
  AuthError,
} from '@urantia/auth/server'

const appId = 'my-app'
const appSecret = process.env.URANTIA_APP_SECRET
const redirectUri = 'https://myapp.com/auth/callback'
const scopes = ['profile', 'bookmarks']
```

<Steps>
  <Step title="Start the sign-in">
    Make the address of the sign-in page. Keep `state` and `codeVerifier` in a short-lived cookie that scripts cannot read, and send the person to `url`.

    ```typescript
    const { url, state, codeVerifier } = await createAuthorizeUrl({ appId, redirectUri, scopes })
    ```
  </Step>
  <Step title="Finish on your return address">
    Check that the `state` in the address is the one that you kept. Then exchange the code.

    ```typescript
    const tokens = await exchangeCode({ appId, code, codeVerifier, redirectUri, appSecret })
    // tokens.accessToken, tokens.refreshToken, tokens.expiresAt, tokens.userId, tokens.email, tokens.scopes
    ```

    Keep the tokens in your own session, for example a sealed cookie that scripts cannot read.
  </Step>
  <Step title="Refresh before the access token ends">
    An access token lasts 15 minutes. A refresh token lasts 90 days from its last use, and each one works one time: a refresh gives you a new pair.

    ```typescript
    try {
      const fresh = await refreshTokens({ appId, refreshToken })
    } catch (error) {
      // Only a refusal ends the sign-in. An outage does not.
      if (error instanceof AuthError && error.kind === 'refused') {
        // Clear your session. The person signs in again.
      }
    }
    ```
  </Step>
  <Step title="Sign out">
    End the sign-in on the service and clear your own session. The person stays on your page.

    ```typescript
    await revokeTokens({ appId, refreshToken })
    ```

    After a sign-out, pass `askAccount: true` to the next `createAuthorizeUrl`. The accounts site then shows its sign-in page, and does not sign the person in by itself.
  </Step>
</Steps>

The [demo](https://demo.urantia.dev) uses this flow. Its source is a small example of each step.

## Browser flow

For an app with no backend. The tokens are in the browser, so use this only where that is acceptable.

```typescript
import { UrantiaAuth } from '@urantia/auth'

const auth = new UrantiaAuth({
  appId: 'my-app',
  redirectUri: 'https://myapp.com/callback',
})

// Popup (the default), or { mode: 'redirect' }
const session = await auth.signIn({ scopes: ['profile', 'bookmarks'] })

// On your return page, for redirect mode
const session = await auth.handleCallback()

// Fires for a sign-in, a refresh, and a sign-out
auth.onAuthStateChange((session) => {})

auth.getSession()        // the session, or null
await auth.signOut()     // stays on your page; the next signIn() is not silent
```

The client keeps the session in `localStorage`, refreshes the access token by itself, and follows a sign-out in another tab.

## Use the token

Send the access token as a bearer token.

```typescript
const res = await fetch('https://api.urantia.dev/me/bookmarks', {
  headers: { Authorization: `Bearer ${accessToken}` },
})
```

Or with `@urantia/api`:

```typescript
import { UrantiaAPI } from '@urantia/api'

const api = new UrantiaAPI({ token: accessToken })
const { data: bookmarks } = await api.me.bookmarks.list()
```

A `401` means that the token ended, or that the person removed your app in their account. Try one refresh. If the refresh is refused, clear your session.

## Sync bookmarks and notes

If your app keeps a copy of a person's bookmarks or notes, ask only for what changed. Pass `since` to the list, and keep the `syncedAt` of the answer for the next sync.

```typescript
const changes = await api.me.bookmarks.list({ since: lastSyncedAt, limit: 100 })
for (const bookmark of changes.data) save(bookmark)        // made or changed at or after since
for (const gone of changes.deleted ?? []) remove(gone.id)  // deleted at or after since
lastSyncedAt = changes.syncedAt
```

- `GET /me/bookmarks?since=` and `GET /me/notes?since=` take an ISO 8601 time.
- `syncedAt` is a little before the time of the read, so an item can come two times. Keep one item for each `id`.
- The service keeps a delete for 90 days. A `since` older than that gets a `410`: get the full list again, without `since`.
- There are no webhooks. Sync when your app opens or when the person asks.

## Permissions

| Permission | What the person reads on the consent screen |
|------------|---------------------------------------------|
| `profile` | See your name, email, and picture |
| `bookmarks` | See and change your bookmarks |
| `notes` | See and change your notes |
| `reading-progress` | See and change your reading progress |
| `preferences` | See and change your reader settings |
| `bookmarks:read` | See your bookmarks |
| `notes:read` | See your notes |
| `reading-progress:read` | See your reading progress |
| `preferences:read` | See your reader settings |

A read-only permission allows `GET` only. A full permission includes its read-only one, so a person who allowed `bookmarks` is not asked again for `bookmarks:read`. Start with read-only permissions if your app only reads.

A token reaches only what its permissions allow. Your app can ask only for permissions that it registered. A new permission later asks the person again.

## What a person can do

A person manages their account at [accounts.urantiahub.com](https://accounts.urantiahub.com). There they see each app that has access, remove one, download a copy of their data as one file, or delete the account. A removal holds at once: your next request with that person's token gets a `401`. A good place for a link to that page is next to your sign-out button.

## Data, security, and terms

- **Where the data is**: account data is in a Postgres database at Supabase, in the United States, encrypted at rest. All traffic uses TLS.
- **How it is kept**: row level security is on for every table. App secrets and refresh tokens are stored only as hashes. The service never stores a raw IP address.
- **A breach**: if a breach touches the data of people who signed in through your app, we tell you and them without delay.
- **If the service ends or changes hands**: people get the chance to download or delete their data first.
- **Age**: the service is not for children. It is not directed at anyone under 18.
- **Terms and privacy**: the [Terms of Service](/terms-of-service) and the [Privacy Policy](/privacy-policy) of urantia.dev cover the API and this SDK.
- **License**: the content of the API is CC0 and the code is MIT. You can use all of it, in research and in published work. Credit is not required, and a link to urantia.dev is welcome.
- **References**: the `/me` routes take a paragraph as `2:0.1`, `2.0.1`, or `1:2.0.1`, and store the global ID (`1:2.0.1`).
- **Reading progress**: each app decides when a paragraph counts as read. The service stores what an app sends.
- **Stability**: a change that breaks a route comes as a new route, never as a change of the old one. Changes are in the [changelog](/changelog).
- **Rate limit**: 200 requests a minute for each caller address.
- **Review and testing**: other people can use your app after a review. Until then, you, the owner, can sign in to it.

## Check a token in your own backend

If your backend receives an access token from your own client, verify it before you trust it.

```typescript
import { createTokenVerifier } from '@urantia/auth/server'

const verify = createTokenVerifier({ appId: 'my-app' })
const claims = await verify(accessToken)   // throws for a token that is not good, or not for your app
```

## Options of the browser client

| Option | Type | Required | Default |
|--------|------|----------|---------|
| `appId` | `string` | Yes | None |
| `redirectUri` | `string` | Yes | None |
| `loginUrl` | `string` | No | `https://accounts.urantiahub.com` |
| `apiUrl` | `string` | No | `https://api.urantia.dev` |

## Security notes

- **PKCE and state**: each sign-in uses a new PKCE verifier and a new `state`. A return with no `state`, or with another one, is refused.
- **Short tokens**: an access token lasts 15 minutes. A refresh token works one time. If an old one comes back, the service ends that sign-in.
- **The secret stays on your server**: the server flow never sends it to a browser.
- **Review**: each app is reviewed before other people can use it, and each later change to what people see or to what the app can reach.
